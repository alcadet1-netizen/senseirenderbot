## 2. Архитектура и где образуется задержка

`src/main.py` создаёт aiogram dispatcher, Mongo-клиент, HTTP Mini Apps, регистрирует middleware и фоновые циклы; `Container` лениво создаёт сервисы. Telegram updates принимаются long polling; MongoDB через Motor — общее хранилище; API/AI, Telegram и виджеты — внешние или CPU-зависимые операции.

Важно: aiogram имеет outer и inner middleware. В `src/main.py:241–284` часть проверок выполняется до маршрутизации update, а `dp.message.middleware(...)` относится к inner-цепочке, то есть применимость зависит от маршрутизации и найденного обработчика. Нельзя утверждать, что весь следующий список выполняется буквально для каждого Telegram update. Для подходящего группового сообщения критический путь включает:

1. `GroupAdminMiddleware` — `get_chat_member` при холодном/истёкшем локальном кэше. Уже реализованы TTL, ограничение размера и single-flight (`src/bot/middlewares/group_admin.py`); этот механизм не следует удалять ради скорости.
2. `ModerationMiddleware` — `is_muted` и Mongo `find_one` для подходящих групповых сообщений (`src/bot/middlewares/moderation.py`, `src/services/moderation_service.py:270`).
3. `UserActivityMiddleware._process_user_activity` — запись активности участника, чтение статуса бана, limiter награды, `process_message_reward`, проверка достижений; для `/`-команд activity пропускается (`src/bot/middlewares/user_activity.py:862–944`). Эти операции в основном ожидаются последовательно.
4. `ChatActivityMiddleware` — запись активности чата и затем запись активности Banzai; внутри Banzai две Mongo-операции уже выполняются через `gather` (`src/bot/middlewares/chat_activity.py`, `src/services/banzai_service.py:81–120`). Комментарий «в фоне» в middleware неверен: здесь стоит `await`.
5. `DigestMiddleware` — добавляет ограниченные по длине тексты в память, затем может запустить генерацию; `PopugaiMiddleware` проверяет шанс и при необходимости дополнительно обращается к Mongo/Telegram. Они выполняются до следующего обработчика, если запрос дошёл до этой inner-цепочки.
6. Обработчик команды/игры может добавлять собственные Mongo, Telegram, AI и рендер-вызовы. Для ответов в личке путь иной: капча, подписка, лимитер, обработчик.

Отсюда основной кандидат на задержку — накопление последовательных сетевых round-trip, особенно при удалённой БД. Это гипотеза по коду, не измеренный p95. `LoggingMiddleware` уже считает общую длительность, а `user_activity._timed_activity_stage` пишет предупреждение после 1 секунды, но это не распределение p95 и не разбор подопераций.

## 3. Приоритетные находки

### P0 — корректность перед ускорением

**3.1. Подписка: limiter используется вместо кэша фактического результата.** `src/bot/middlewares/subscription.py:62–108`, `src/services/throttle_service.py:19–40`. `throttle` возвращает `True`, когда операция разрешена, но middleware при этом считает пользователя подписанным без проверки. При `False` выполняет Telegram-проверку. Кроме ошибки допуска это даёт лишние Telegram-вызовы в течение окна. `restricted` также надо оценивать с учётом `is_member`.

Решение: отдельный bounded TTL-кэш именно фактического статуса `(channel,user)` с явной политикой positive/negative TTL, single-flight и инвалидированием на подтверждение/изменение подписки; отдельно определить fail-open/fail-closed при ошибках Telegram. Не использовать limiter как membership cache. Проверить первый запрос, повторы, отписку, restricted и конкурентность. Эффект: меньше внешних запросов, но прежде всего исправление доступа.

**3.2. Ограничение команд не ограничивает выполнение.** `src/bot/middlewares/throttling.py:38–72`: при `can_proceed=False` может отправляться предупреждение, но далее всё равно вызывается `handler`. Под нагрузкой спам-команды продолжают расходовать ресурсы. Это наблюдение относится к данному middleware; у отдельных команд могут быть собственные ограничения.

Решение: определить продуктовую политику для отклонённых команд и вернуть управление без выполнения handler, сохранив исключения для платежей, капчи и важных callback. Тестировать порядок middleware и работу групп/лички. Не включать блокировку вслепую — изменится поведение пользователей.

**3.3. Достижения: N+1 и риски выплаты.** `AchievementService.check_and_unlock_achievements` (`src/services/achievement_service.py:61–222`) повторно читает пользователя и вызывает `has_achievement` отдельно для каждого выполненного условия; разблокирование ещё раз проверяет наличие и определение (`src/domain/repositories/achievement_repository.py:37–65`). Число запросов зависит от профиля. В текущем коде есть дополнительные несогласованности, требующие воспроизведения на реальной тестовой БД:

- `UserRepository.update` выбирает `_id` в качестве `user_id`, но фильтрует по полю `id` (`src/domain/repositories/user_repository.py:94–110`). Для обычного Mongo ObjectId и числового Telegram `id` обновление может не найти документ. Возвращаемый `False` в сервисе не проверяется.
- Сервис читает `reward_coins`/`reward_xp`, а `AchievementRepository.add_achievement` записывает `coin_reward`/`xp_reward` (`achievement_repository.py:92–102`). Реальное содержимое коллекции надо проверить: при таком формате награда может считаться нулевой.
- Разблокировка, списание из банка, обновление игрока и запись журнала не объединены в одну транзакцию. Возможны частичные результаты при сбоях; наивное распараллеливание усугубит риск.

Решение: сначала воспроизвести с настоящей MongoDB и исходной схемой, проверить существующие документы и дубликаты. Затем сделать одно чтение уже открытых ID, единый индекс/атомарную идемпотентную разблокировку и транзакционное начисление с журналом; проверить миграционную совместимость полей. Не выполнять автоматические ретроначисления без отдельной сверки. Ожидается значительное уменьшение N+1-запросов; количественную выгоду замерить.

**3.4. Прочие денежные операции нельзя ускорять удалением транзакций.** Текущий `process_message_reward` уже объединяет дебет банка, кредит игрока, счётчик и журнал в Mongo-транзакцию (`src/services/economy_service.py:212–272`); старый аудит, утверждающий обратное для этого пути, устарел. Но другие операции отличаются: например, `buy_katana` и `confiscate_on_ban` используют последовательные независимые записи (`economy_service.py:490–550`). Локальные asyncio locks не координируют процессы. Перед горизонтальным масштабированием — инвентаризация всех денежных путей, идемпотентность, tests replica-set, reconciliation и контролируемые миграции. Не параллелить debit/credit через `gather`.

**3.5. Доступ к добавлению вопросов.** В `src/bot/handlers/quiz.py:39–42` у `/addquestion` нет административного фильтра; последующие состояния также его не проверяют. Если команда задумана административной, это прямой обход, а фото ещё и скачивается в локальную файловую систему (`quiz.py:74–82`). Уточнить продуктовые права, затем проверять их на каждом FSM-шаге; ограничить размер/хранение фото. Это не основной источник latency, но важно до нагрузочного роста.

### P1 — сокращение работы на горячем пути

**3.6. Профиль записывается даже без изменений.** `EconomyService.process_message_reward` (`src/services/economy_service.py:161–199`) на существующем пользователе безусловно формирует `$set` для непустых имени/username, даже если они уже такие же. Это дополнительная ожидаемая запись Mongo для каждого подходящего вызова, включая ветку без награды. Сравнивать значения с уже прочитанным профилем и записывать только изменения, сохранив прежнюю семантику `None` и конкурентных обновлений. Тесты: имя не изменилось/изменилось, конкурентная обработка. Проверять нагрузку write operations и p95, а не только локальное время функции.

**3.7. Бан и профиль читаются отдельно.** `unban_if_active_in_chat` делает `find_one` по пользователю на каждый подходящий вызов, затем reward читает профиль снова (`src/services/moderation_service.py:118–148`, `economy_service.py:161–163`). Рассмотреть общий request-scoped snapshot с минимальной проекцией или перестановку операций, только после проверки взаимодействия автобана, транзакционного перечитывания и конкурентных изменений. Не использовать устаревший локальный кэш банов как единственный источник истины.

**3.8. Активность чата и Banzai.** `ChatActivityService.update_activity` и `update_user_activity` делают upsert (`src/services/chat_activity_service.py:33–45, 170–178`); Banzai вставляет событие активности на каждое подходящее сообщение и обновляет активную игру даже если её нет (`src/services/banzai_service.py:81–120`). Сначала измерить долю этих запросов и планы индексов. Рассмотреть ограниченное по времени объединение только неавторитетных отметок активности; для тишины Banzai сохранять точный порядок, номер раунда и реакцию на каждое сообщение. Пакетирование записи может потерять последние события при аварии: нужен явный допустимый предел потерь и тесты перезапуска. Простая отложенная `create_task` без лимита не решение.

**3.9. Banzai TTL не удаляет числовые timestamps.** Вставляется `int(time.time())`, а TTL-индекс построен на `timestamp` (`src/services/banzai_service.py:96–106, 127–134`). Mongo TTL работает с BSON Date, так что накопление записей вероятно; фактический объём БД неизвестен. Ввести отдельное Date-поле для TTL или совместимую миграцию с dry-run, учесть старые записи и существующие запросы по числовому timestamp; проверить планы и рост коллекции. Не удалять документы без плана и backup.

**3.10. Popugai.** `get_reply_chance` делает до двух последовательных чтений при отсутствии записи (`src/services/popugai_service.py:20–25`); вызывается для подходящих сообщений (`src/bot/middlewares/popugai.py:14–43`). Подойдёт bounded TTL-кэш с кэшированием отсутствия, single-flight и инвалидированием при `set_reply_chance`. Нужна стратегия согласованности между экземплярами. Выбор медиа уже происходит на стороне Mongo через `$sample`, а не выгрузкой всех документов; проверить explain и стоимость `$sample` после `$match` на больших чатах, прежде чем менять распределение случайного выбора.

**3.11. Статистика и обращения.** `EconomyService._get_total_coins_in_circulation` имеет 10-секундный single-flight; `StatsService.get_admin_stats` — 60-секундный кэш и lock (`src/services/economy_service.py:295`, `src/services/stats_service.py:35–55`). Не удалять эти оптимизации. На cache miss `StatsService._read_admin_stats` всё ещё сканирует users и агрегирует transactions в snapshot-транзакции. При росте коллекций измерить длительность/нагрузку; если она существенна — обсудить материализованные счётчики с журналом, сверкой, явно обозначенной свежестью и восстановлением, не подменяя финансовую истину приблизительной статистикой.

**3.12. Локальные locks растут вместе с аудиторией.** `EconomyService._get_lock` (`src/services/economy_service.py:58–71`) сохраняет lock в словаре без удаления; используется с ключами пользователей в нескольких методах. Долгоживущий процесс может накапливать неограниченное число записей. Использовать безопасный registry с очисткой только после завершения всех ожидающих, например weak references при сохранении сильных ссылок на время использования, либо stripes с принятым уровнем ложной конкуренции. Проверить одновременное ожидание и удаление; lock в любом случае не заменяет межпроцессную атомарность.

### P1 — фоновые задачи, память, массовые операции

**3.13. Рассылка.** `BroadcastService.get_users` загружает полные документы в список (`src/services/broadcast_service.py:56–64`), затем отправляет последовательно с задержкой не менее 0,05 с на получателя (`:77–110`). Миллион отправок — минимум ~13,9 часа только на sleep; это арифметическая нижняя граница, а не измерение. `_pending` один на весь экземпляр, прогресс не durable.

Решение: отдельный durable job в Mongo с автором/черновиком, проекцией `id`, cursor/batch и checkpoint; ограниченный rate и обработка Telegram RetryAfter, учёт заблокированных пользователей, отмена/возобновление и явная семантика повторной отправки при неизвестном результате. Не обещать exactly-once при сетевом таймауте. Моделировать запуск и отказ без реальной рассылки.

**3.14. Напоминания о неактивных чатах.** `_check_chats` загружает все подходящие записи и последовательно делает `get_chat` и отправку (`src/services/chat_activity_service.py:110–145`). Постраничный cursor с проекцией и ограниченный пул отправок помогут контролировать память и время прохода, но нужны per-chat claim/ограничение скорости и безопасное сравнение времени активности при гонке. На shutdown есть `stop_monitoring`, но явного вызова в `on_shutdown` не найдено (`src/main.py:127–151`): протестировать отсутствие фоновых задач после остановки.

**3.15. Автосбор dojo.** `auto_tick` уже использует потоковый cursor, а не `to_list`, но последовательно вызывает `auto_step` для каждого пользователя (`src/services/dojo_miner_service.py:689–709`). При большой аудитории длительность обхода может быть больше интервала. Измерить lag и операций на игрока, затем рассмотреть индексируемую выборку реально наступивших сроков, небольшую ограниченную конкурентность и durable claim. Сохранить идемпотентность сбора и проверить рестарты, fairness и Telegram/Mongo лимиты.

**3.16. Лотерея.** `run_lottery` материализует все активные билеты, перемешивает список, потом последовательно обновляет билеты и читает пользователей (`src/services/lottery_service.py:26–67`). При больших объёмах — память O(N) и много запросов; конкурентные розыгрыши могут выбирать один билет. Рассмотреть потоковый reservoir sampling O(k) или другой проверенный равномерный алгоритм, пакетное чтение профилей и атомарные условия/изоляцию розыгрыша. Потребуются статистические тесты честности и тесты гонок; не менять вероятность выигрыша и правила билетов ради оптимизации.

**3.17. Digest и фоновые уведомления.** `DigestService` хранит до 1000 сообщений на чат в deque, но словарь чатов не ограничен глобально (`src/services/digest_service.py:278–315`); данные теряются при перезапуске. `DigestMiddleware` и отправка уведомлений создают фоновые задачи (`src/bot/middlewares/digest.py:59`, `user_activity.py:978`). У digest есть защита `generating` внутри самой корутины (`digest_service.py:501–504`), но до её запуска можно создать дополнительные короткоживущие задачи. Ввести метрики числа чатов/задач и bounded task registry с обработкой ошибок и graceful shutdown; ограничение глобального хранения и срок жизни — с учётом приватности и требований к восстановлению. Не записывать историю чатов в durable-хранилище без решения по политике хранения.

**3.18. Внешние API.** `src/api/crypto_api.py`, `src/core/providers.py`, `src/services/xrocket_service.py` создают `aiohttp.ClientSession` во многих вызовах. Переиспользуемая session с закрытием при shutdown может уменьшить handshake и количество соединений. Ввести timeout, ограничение конкурентности, метрики и backoff с учётом специфики API; денежные запросы не повторять автоматически без idempotency key и обработки неизвестного результата. Эффект зависит от частоты и latency, требует замера.

**3.19. Рендер и event loop.** Катана уже использует `asyncio.to_thread`, общий `Semaphore(2)` и fallback (`src/bot/presenters/katana_presenter.py:16–52`, `src/widgets/limits.py`). Измерить отдельно ожидание слота, CPU render, размер и Telegram upload; не считать общую длительность GIF временем только CPU. Если загрузка слотов высокая — ограничить размер очереди/показывать статический вариант или кешировать повторяемые публичные ресурсы. Не кэшировать персональный финансовый receipt без корректного ключа и правил приватности.

### P2 — эксплуатация, индексы и reproducibility

**3.20. Индексы.** Проверить фактические индексы, количество документов и `explain('executionStats')` на изолированном стенде или безопасной реплике: кандидаты — `chat_activities(chat_id)`, `chat_activities(last_activity)`, `chat_user_activities(chat_id,user_id)`, `(chat_id,last_activity)`, `user_achievements(user_id,achievement_id)`, `tickets(user_id,burned)`, а также конкретные запросы users/transactions. Это кандидаты, а не инструкции к немедленному созданию: селективность, размеры и уже имеющиеся индексы неизвестны; каждый индекс увеличивает стоимость записи. Перед unique — read-only поиск дублей и отдельный план устранения. В `chat_settings_service.py:17` и `captcha_service.py:64–65` есть вызовы `create_index` из sync-конструктора без явного ожидания результата; проверить фактическое поведение Motor и ошибки. Индекс Banzai запускается фоновой задачей в конструкторе. Лучше централизованный async startup manifest с диагностикой и проверкой результата, не блокирующий запуск некритичных функций без решения по политике.

**3.21. Управление нагрузкой.** В вызове `dp.start_polling` (`src/main.py:335–344`) нет явно заданного предела конкурентности update; поведение зависит от установленной версии aiogram. Измерить количество активных задач, состояние очереди/lag и соединения; подобрать ограничение только совместно с тестом долговременных обработчиков, платежей и доставки Telegram. Бесконтрольное число задач увеличивает память, но слишком маленький предел тоже может задержать важные updates.

**3.22. Mongo и deployment.** `MongoClient.connect` использует стандартные настройки Motor (`src/infra/mongo/client.py`); пул, таймауты, регион БД и retry надо подбирать по метрикам, а не увеличивать вслепую. `docker-compose.yml` запускает standalone Mongo, тогда как транзакционные пути требуют replica set/mongos; документировать и проверять готовность окружения. `/health` возвращает `OK` без проверки зависимостей (`src/main.py`): разделить liveness/readiness, не превращая частые проверки в дорогой DB scan.

**3.23. Зависимости и повторы проверки.** `requirements.txt` в основном задаёт только нижние границы версий; CI и production могут получить разные сочетания пакетов. Использовать lock/constraints для Python 3.12, отдельно тестировать обновления; зафиксировать pytest-asyncio loop scope и предупреждения. Обновить benchmark, чтобы база не зависела от недоступного коммита, а текущие моки поддерживали сессии/транзакции; отдельно держать сценарий реального staging Mongo. Не выдавать тест на `asyncio.sleep` за нагрузочное испытание.

**3.24. Логирование.** На горячем пути есть многочисленные INFO до/после этапов и результат с пользовательскими данными (`src/bot/middlewares/user_activity.py`, `src/services/economy_service.py:152,292`, `src/bot/middlewares/logging.py`). Измерить объём логов, event-loop lag и стоимость сериализации/вывода. Перевести подробные события в sampled debug, оставить агрегированные метрики, slow/error logs и минимальные идентификаторы; не логировать текст, токены, имена и баланс без необходимости. Сохранить полезный аудит финансов отдельно.

## 4. Матрица остальных функций и дальнейшая глубина

- **Регистрация, профиль, уровни:** `user_service`, `user_repository`, `level_service`; профиль делает несколько чтений счётчиков. Считать round-trips и проверить согласованность, особенно регистрацию и стартер при гонках.
- **Ежедневные награды, платная Ежа, Stars, донаты:** `daily_service`, `daily_pet_service`, `paid_hedgehog_service`, `star_coin_service`, handlers; сначала платежные idempotency, timeout и повторная доставка. Никаких оптимизаций без replica-set тестов.
- **Дуэли, слоты, рулетка, бомба, волна, обмен, торговля:** `duel_service`, `duel_escrow`, `slots_service`, handlers и `exchange_service`. Проверить lifecycle задач, состояние после рестарта и порядок денежных операций; не предполагать, что один локальный lock защищает несколько экземпляров.
- **Боссы, викторина, Banzai:** монитор дедлайнов, кэши и рост активности; тестировать восстановление, дубликаты и остановку, затем профилировать.
- **Кампании комментариев:** `comment_campaign_service`, `campaign_polling`, `comment_campaign_inbox`; важны backlog, lease/retry, долг очереди и deadline. Durable ingress нельзя переносить в fire-and-forget ради latency.
- **AI/Sage/Fly, digest:** latency провайдера, лимиты токенов и конкурентность, privacy, timeout; не передавать данные production в искусственные тесты.
- **Mini Apps dojo/hedgehog/daily pet и виджеты:** замеры API по endpoint, отклик рендера, upload, память и конкурентность. JS-скрипты прошли, но визуальное поведение в Telegram отдельно не проверялось.
- **Рефералы, достижения, банк, эмиссия:** целостность и reconciliation важнее количества round-trips; проверять деньги под конкуренцией до горизонтального масштабирования.
- **Модерация, капча, подписка, права группы:** время и нагрузка проверок; позитивные и негативные cache TTL выбираются с явным безопасным поведением при сбоях.
- **Рассылка, напоминания, автоматические майнеры:** throughput и lag с учётом Telegram limits; курсоры, checkpoint, ограниченные воркеры и контроль дубликатов.

Этот раздел — карта приоритетов для следующей итерации, не утверждение о построчной проверке каждой функции.

## 5. План внедрения и проверки результата

1. **Базовые измерения до изменений.** На staging с Python 3.12, изолированным Mongo replica set и Telegram mock измерить p50/p95/p99 end-to-end и по этапам: moderation, user activity, rewards, achievements, chat activity, Banzai, Popugai, handler; запросы Mongo/update, pool wait, event-loop lag, RSS, активные задачи, задержку очередей и ошибки API. Использовать разные типы событий, долю команд, медиа, новых и известных игроков, горячий/холодный кэш. Не использовать ID или тексты реальных пользователей.
2. **Небольшие безопасные исправления.** Подписка и командный throttle с тестами, затем исправление/сверка достижений и оптимизация неизменённых профильных записей. Каждый пункт — отдельный PR, сравнение выходов и обратимый rollout. Для денег — транзакционные, конкурентные и fault-injection тесты с реальной Mongo.
3. **Индексы и TTL.** Сначала инвентаризация, `explain`, размер и рост, поиск дублей, staging dry-run и backup; затем совместимые индексы/миграция TTL при мониторинге write latency.
4. **Массовые операции и background lifecycle.** Рассылка с checkpoint, потоковые напоминания, bounded registry, измерение lag dojo. Отдельно протестировать падение между записью и внешней отправкой, cancel/shutdown, повтор и Telegram RetryAfter.
5. **Нагрузочный эксперимент.** Для примера провести ступени 1/10/50 подходящих updates в секунду и длительный soak — это сценарии проверки, не ожидаемая вместимость. Измерить насыщение, сравнить baseline/candidate на одной инфраструктуре, зафиксировать SLO и откат. Добавить тесты при медленной/недоступной Mongo/Telegram и всплесках одного чата/пользователя.
6. **Масштабирование экземпляров — последним.** Сначала устранить неоднозначные monetary paths, общую память игровых состояний, дубли фоновых задач и конфликт polling. Один процесс с исправленными hot paths может оказаться быстрее и безопаснее нескольких без координации.

Никаких заявлений о процентах ускорения и допустимом числе пользователей без замеров делать нельзя. Ожидаемый эффект перечисленных пунктов — уменьшение лишних round-trips, количества записей, потребления памяти и хвостовых задержек, но не гарантированная конкретная скорость.
