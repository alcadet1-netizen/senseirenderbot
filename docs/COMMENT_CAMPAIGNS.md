# Автоматические Coin-акции в комментариях SenseiDurova

## Архитектура и область изменений

Python/aiogram 3, Motor/MongoDB, существующие `users.id`, `users.coins`, `transactions`. Новая параллельная валюта/баланс не создаётся. Используется существующий `UserService.get_or_create`, включая обычные стартовые условия регистрации. Награды кампании выдаются **из SenseiBank** (`bank/_id=single`, поле `coins`), того же банка, который показывает `/senseibank`. Автопополнения и эмиссии нет. В журнале `tx_type=comment_campaign_reward`, `xp_change=0`.

Планировщик — MongoDB-backed job queue (`due_at`, lease, фазы), без Redis/Celery. Входящие Telegram-события и известные удаления также хранятся в MongoDB. SQLite, локальный файл очереди и Render Persistent Disk не используются.

Главные файлы:
- `src/services/comment_campaign_service.py` — обнаружение, сбор, выбор победителя, транзакционные выплаты, scheduler/recovery;
- `src/infra/comment_campaign_inbox.py` — MongoDB ingress и подтверждённые удаления самим ботом;
- `src/bot/middlewares/comment_campaign.py` — захват Update до игровых фильтров/троттлинга;
- `src/bot/middlewares/{cleanup,moderation}.py` — уведомления об успешных удалениях комментариев самим ботом;
- `src/core/{config,container}.py`, `src/main.py` — конфигурация, DI, startup/shutdown, channel_post updates;
- `scripts/migrate_comment_campaigns.py`, `scripts/start_test_mongo.py` — миграция и тестовый replica set;
- `tests/campaign_support.py`, `tests/unit/test_comment_campaigns.py`, `tests/integration/test_comment_campaigns.py` — общие сценарии на fake и настоящей БД.

## Как определяется обсуждение

При первом запуске `getChat(@SenseiDurova)` используется только как discovery, если числовой ID ещё не задан/не сохранён. Затем числовые ID канала и связанной supergroup закрепляются в MongoDB `settings/_id=comment_campaign_channel`; после перезапуска используется закреплённый ID, а не потенциально сменившийся username. При явных env-ID проверяется реальная связь `linked_chat_id`.

`channel_post` сохраняет наблюдение публикации. Акция создаётся **только** после `is_automatic_forward=true` в нужной discussion group и `MessageOriginChannel.chat.id == TARGET_CHANNEL_ID`. ID исходной публикации берётся из `forward_origin.message_id`, время начала — из `forward_origin.date`. Ручные пересылки и чужие каналы акции не создают.

Связь комментария с акцией — `message_thread_id` либо ответ на корневое сообщение/объявление/уже известного участника цепочки. Маршруты ответов сохраняются в БД, включая промежуточные сообщения ботов/служебные сообщения (сами они не награждаются). Просто сообщение в группе без связи с этим тредом не считается. Если Telegram не передал thread ID и родительское сообщение вообще не было получено ботом, нельзя надёжно угадать тред — такой комментарий не учитывается.

Пересланные части альбома с общим `media_group_id` discussion group объединяются в одну акцию. Все исходные message ID сохраняются как aliases в `campaign_posts`; маршруты всех частей ведут к одному campaign ID. Разные посты/треды обрабатываются независимо.

Bot API не предоставляет `getDiscussionMessage` и историю произвольного треда. Если автоматическая пересылка не появилась, через 60 секунд в журнале предупреждение `no_discussion_observed`; акция не создаётся. Это может означать отключённые комментарии, отсутствие доставки или прав, а не доказанный ответ Telegram «комментарии отключены». Новая пересылка, пришедшая позже, но до deadline, всё ещё может создать акцию.

## Правила и тексты

По умолчанию:
- начало: время публикации, конец: `started_at + 4 часа`;
- окно `[started_at, deadline)`; сообщения ровно в deadline уже не включаются;
- каждый отдельный человеческий комментарий — отдельная единица, включая несколько комментариев одного участника и отдельные сообщения медиаальбома-комментария;
- боты (включая текущего), anonymous sender_chat, автоматические пересылки, платежные/служебные сообщения исключены;
- допустимый пользовательский контент перечислен в config; сервисные типы не включаются даже при ошибочном добавлении в список;
- существующие banned-профили не участвуют в выборе победителя; блокировка после выбора приостанавливает выдачу такому профилю;
- единица-победитель получает **2000 вместо 100**, остальные — по 100;
- в `REWARD_PER_UNIQUE_USER=true` выбирается первый подходящий комментарий пользователя (по message ID), он один участвует и в базовой выплате, и в выборе победителя;
- `WINNER_REWARD_MODE=bonus`: победителю 100 + 2000 = 2100; остальные по 100;
- параметры наград и режима сохраняются snapshot в акции: смена env не переигрывает уже начатую акцию.

Уведомления сокращены по последнему запросу: только условия, срок и результат. Имя экранируется и упоминается через `tg://user?id=...`. Если есть pending-регистрации или заблокированные выдачи, текст честно дополнен оговоркой, а не заявляет о совершённых выплатах. При нуле валидных комментариев используется отдельный текст «награды не начислены».

### Удалённые комментарии

**Общих updates об удалении обычных group messages и надёжного read-only `getMessage` в Bot API нет.** Произвольные чужие удаления проверить нельзя. Поэтому по умолчанию полученный комментарий остаётся учтённым, если нет известного удаления до фиксации итогового набора.

Успешные удаления самим ботом в `CommandCleanupMiddleware` и `ModerationMiddleware` записываются в durable inbox/tombstones и исключаются до sealing. Удаления другими администраторами, пользователем, Telegram или иными неинструментированными участками кода не отслеживаются. После sealing набор/победитель заморожены; удаления не меняют уже зафиксированную выборку и выплаты. Удалять/пересылать сообщения для «проверки существования» бот не будет: это побочный эффект, а не надёжная read-only проверка.

## Гарантии денег и восстановление

- MongoDB **replica set или mongos**, sessions, транзакции `snapshot` + `majority`. Standalone — функция не запускается, без небезопасного fallback; при включённом feature polling не запускается до успешной проверки.
- Уникальный campaign ID связан с channel/post. Winner выбирается reservoir sampling через `secrets.randbelow`, только по зафиксированным eligible-комментариям, пакетами. Счётчик выборки и текущий кандидат сохраняются транзакционно; после завершения планирования победитель не меняется при retry.
- Сбор комментариев пишет version fence в campaign. Sealing также пишет campaign внутри транзакции, поэтому они не могут независимо закоммититься на устаревшем snapshot.
- Операция начисления: `_id=comment_campaign:{channel_id}:{post_id}:{comment_id}:{kind}`. Для total winner — только `winner_total`; base ему не создаётся. Для bonus — отдельные `base` и `winner_bonus`.
- **Каждая операция**: условное списание SenseiBank при достаточном остатке, user `$inc coins`, запись rewards и уникальный журнал — одна Mongo transaction. Нет попытки вместить неограниченную 4-часовую кампанию в одну огромную Mongo transaction. При сбое часть операций может быть уже выплачена, но кампания остаётся незавершённой; повтор безопасно завершает остальные, не удваивая завершённые. `completed` выставляется после обработки всех операций и публикации результата.
- Статусы `active / processing / completed / failed`; фазы announcement/wait/plan/payout/final. На ошибка Telegram/DB сохраняется причина и retry time; после перезапуска просроченные/processing/failed нетерминальные задачи подхватываются автоматически.
- Один lease owner на campaign, атомарный claim, expiry и write fencing внутри финансовых транзакций. Протухший воркер не может начислять после захвата новым. Работа пакетная, lease продлевается между выплатами.
- Финальное сообщение не управляет идемпотентностью выплат. Если его отправка не удалась, повторяется только незавершённая стадия final.
- Telegram `sendMessage` не имеет ключа идемпотентности: если Telegram принял сообщение, а соединение/запись message ID оборвались, при retry возможно повторное объявление. Это **не** повторная награда. При недоступном root итог заменяет собственное стартовое объявление; если это невозможно, доставка блокируется для ручной проверки, без публикации в чужом треде (см. восстановление final ниже).

### Регистрация

Комментарий сначала сохраняется, затем вызывается существующий `UserService.get_or_create`. Его обычные starter rewards не заменяются и не считаются наградой кампании. Если профиль создать нельзя, комментарий не теряется; операция имеет `pending_registration`. После нормальной регистрации worker выдаёт pending транзакционно (повторный worker не удваивает награду). Итоговое сообщение дополнено инструкцией `/start`. Banned-выдачи остаются `blocked_banned`; автоматического разбанивания/выплаты таким профилям нет.

### Очередь и временные ограничения

После deadline даётся `CAMPAIGN_SETTLEMENT_GRACE_SECONDS` на дренирование входящих событий; **время допустимых комментариев не продлевается**. После рестарта сначала дренируется MongoDB inbox. Sealing откладывается, если в нём ещё есть необработанные события. Нормальная задержка подведения — grace + polling + работа очереди. «Ровно по часам» без учёта сети и очереди не обещается.

Mongo inbox сохраняет update в majority-транзакции **до** возврата события из polling intake в Dispatcher. При ошибке Mongo intake удерживает текущий update и повторяет запись; следующий offset не подтверждается до commit. События уже в очереди переживают рестарт. Telegram хранит updates ограниченное время; бесконечный offline восстановить нельзя. Один poller и один drainer/основной campaign worker на bot token; конкурентные транзакции sealing/ingress защищены общим Mongo write fence. Не запускайте старую SQLite-версию параллельно с новой MongoDB-версией.

`BOT_TOKEN`, `MONGO_URI`, `MONGO_DB` — прежние настройки проекта. Пароли/токены в чат не присылать. Нового Redis URL/API-ключа не требуется. `CAMPAIGN_ALLOWED_CONTENT_TYPES` позволяет сузить список допустимых пользовательских типов. 1. Подготовить MongoDB replica set/mongos и backup; проверить/применить миграцию.
2. Подключить discussion supergroup к каналу в настройках Telegram.
3. Добавить бота **администратором канала и группы**. В канале — право публикации; в группе — доступ к сообщениям и отправке ответов/сообщений. Group admin даёт полный поток сообщений без ограничения privacy mode. Право удаления нужно только для уже имеющейся модерации, не для основного розыгрыша.
4. Проверить доступность MongoDB replica set, свободное место и мониторинг очереди; persistent disk не нужен.
5. Установить env, включить feature и запустить обычный `bash start.sh` (или штатный Render start command). Отдельный cron/scheduler не нужен.
6. Проверить startup `Comment campaigns ready channel=... discussion=...`; при ошибке startup исправить topology/права/связь/индексы и перезапустить. Не считать вывод успешных unit-тестов подтверждением прав живого бота.
7. Опубликовать новый тестовый пост. Для staging можно уменьшить duration; проверить объявление именно под ним, journal/rewards и final IDs. Вернуть duration=4 до production. Уже начатые акции не меняют snapshot.

Для публикаций до первого включения feature акции не создаются. Если первоначальное объявление не удалось доставить до конца окна, campaign остаётся terminal failed и выплаты не запускаются. Временные ошибки финальной доставки повторяются независимо от уже обработанных выплат; постоянная недоступность root и собственного объявления требует ручной проверки.

## Исправления повторного ревью

- Sealing в одной majority Mongo transaction пишет общий inbox revision fence, проверяет обе очереди и меняет campaign phase. Все put/ack/deletion используют тот же fence: snapshot-проверка не допускает конкурентного незамеченного insert. Mongo sealing ограничен 15 секундами.
- Граница участия — события, **durably admitted до барьера** с Telegram date внутри окна. События, не принятые до этой границы (в том числе ещё находящиеся в Telegram), не переигрывают уже зафиксированную выборку. Grace уменьшает риск поздней доставки, но не заменяет недоступную Bot API историю.
- Старые roots/aliases существующей акции восстанавливаются и после deadline; запрет ретроакции применяется только к созданию новой акции.
- UUID хранится в Mongo `settings/_id=campaign_inbox:{bot_id}`: существующая identity сохраняется. Startup добавляет backend=mongodb/schema_version=2, не меняя кампании/привязки/балансы. UUID нового проекта генерируется только при отсутствии binding.
- Поддерживаются один poller и один drainer/основной worker на bot token; для multi-drainer HA потребуется отдельный lease/claim протокол. Общего файлового диска нет.
- Параметр grace используется из snapshot уже начатой акции, не из новых env.

Пример стартового уведомления:

> 🎉 Coin за комментарии
>
> 100 Coin за каждый комментарий.
> Одному случайному комментарию — 2000 Coin вместо 100.
> Итоги через 4 ч.

Пример результата:

> 🏆 Итоги
>
> Победитель: Имя — 2000 Coin.
> Coin начислены участникам.

Без участников: «🏁 Розыгрыш завершён. Подходящих комментариев нет — начислений нет.» При pending/blocked выдачах не заявляется, что все средства выплачены; добавляется короткая инструкция/оговорка.

SQLite UUID mismatch больше не возникает: runtime использует существующую Mongo identity. Ошибки прав/topology при включённой функции по-прежнему останавливают startup; временные ошибки повторяются.

## Финансирование из SenseiBank

При выплате bank.coins уменьшается ровно на сумму, зачисленную пользователю. В журнале сохраняются `funding_source=senseibank` и `bank_change=-amount`. Повтор paid-операции не списывает банк повторно. Отсутствующий или недостаточный банк не создаётся/не сбрасывается: кампания остаётся незавершённой и повторяет выплату после пополнения. Pending-награды списывают банк только при фактической выдаче; при нехватке переходят в `pending_bank` и автоматически проверяются снова.

Ранее выданные emission-награды с `status=paid` не списываются задним числом: финансовые записи не переписываются. Установить новую версию нужно на всех campaign workers одновременно, без смешанного rolling rollout. Стартовые бонусы существующей регистрации и legacy-операции других игр этой правкой не изменяются.

## Нет объявления под новым постом: диагностика

1. В deployment environment должно быть `COMMENT_CAMPAIGNS_ENABLED=true`. Значение по умолчанию **false**, `.env.example` не включает выплаты автоматически. В логах выключенного feature теперь явное `Comment campaigns OFF`.
2. После запуска должна появиться строка `Comment campaigns ready channel=... discussion=...`. Числовой discussion должен совпадать с группой комментариев нужного канала. Сам факт получения обычных сообщений группы этого не доказывает.
3. `GET /health/campaigns` возвращает только `enabled`, `ready`, `state`, без токенов, балансов, ID пользователей и текста ошибок. При включённой, но не работающей функции — HTTP 503. Общие `/` и `/health` остаются liveness-проверками и не подтверждают работу розыгрыша.
4. Временные ошибки Telegram/сети/Mongo при инициализации повторяются до трёх попыток. Между обычными retry максимум 5 секунд; Telegram RetryAfter соблюдается. После исчерпания попыток или постоянной ошибки приложение отказывается запускать polling, вместо незаметной потери событий розыгрыша. При остановке startup закрываются web/Mongo-ресурсы.
5. После новой автоматической пересылки в целевую группу: `Campaign automatic forward queued ...`, затем `Campaign observed ...` и `Campaign announced ...`. В логах только IDs, без текста комментария. `root ignored ...` объясняет неподходящий источник/публикацию до первого включения. `CATCH_ALL`/aiogram `not handled` относятся к обычной маршрутизации и сами по себе не означают, что outer middleware не сохранил событие.
6. Объявление больше не ждёт startup grace. Grace применяется только к закрытию набора участников (включая overdue recovery), не задерживая стартовые сообщения.
7. Mongo replica set обязателен; persistent disk и CAMPAIGN_INBOX_PATH больше не нужны. Не удаляйте Mongo binding. Нельзя запустить несколько Telegram pollers одного bot token.

Для предоставленных production-логов: группа `-1002098194464` получает сообщения, но тип/канал пересылки и факт запуска feature из этого фрагмента не установлены. Отправитель `777000` — лишь признак сообщения Telegram, не доказательство нужных `is_automatic_forward` и `forward_origin.chat.id`. Требуются startup-строки или новый `/health/campaigns` после deployment. Настройки/доступ к production этим изменением не меняются, пропущенные исторические треды Bot API прочитать не может.

## Приёмочный сценарий «пост → объявление → 4 часа → выплаты → итоги»

Общий сценарий `test_complete_post_announcement_four_hours_bank_rewards_and_one_result` выполняется на fake и в CI на настоящем MongoDB replica set. Проверяет:

- Входящий channel_post и automatic forward проходят через durable capture/inbox; объявление отвечает на root именно нужной группы.
- Позднее получение automatic forward не сдвигает четыре часа от исходной публикации.
- До deadline денег/финального сообщения нет. Комментарий за секунду до deadline включён, ровно в deadline — исключён.
- При трёх разных участниках два получают по 100, один — 2000 Sensei Coin вместо 100; SenseiBank уменьшается ровно на 2200.
- Штатно отправлены два сообщения: объявление и **один** общий результат с победителем и базовыми наградами остальных комментариев.
- Повторная доставка и повторные задачи не создают новых выплат/результатов.

Capture теперь будит локальный scheduler сразу после durable commit, без ожидания следующего 5-секундного poll. В тесте worker с poll=60 секунд просыпается по root, а не по таймеру. Poll остаётся для overdue jobs, recovery и других worker-процессов. Называть сообщение «гарантированно первым» нельзя: Telegram и участники независимы, люди могут ответить до доставки update боту; также Mongo/Telegram могут быть недоступны.

Условия по умолчанию не изменены: награда за **каждый подходящий комментарий**, несколько комментариев пользователя разрешены; unique-user и bonus — отдельные опции. В production по-прежнему нужны enabled=true, рабочая проверка /health/campaigns, права и MongoDB inbox. При нехватке денег выплаты ждут пополнения, а не обещают несуществующее зачисление.

Аудит общего SenseiBank остаётся открытым: legacy `EconomyService` использует read-modify-$set и автосброс остатка. Это может затереть уже совершённое списание кампании при параллельной игровой операции. Данный приёмочный сценарий проверяет кампанию и её worker-ы, но **не доказывает сохранение денег во всех legacy-играх**; эти операции требуют отдельного исправления и cross-service regression-теста.

При появлении нового root дренирование пакета уступает управление отправке объявления, не ожидая регистрации следующих комментариев. Due-объявления имеют приоритет перед старыми payout-задачами; claim остаётся атомарным/fenced, а индексы создаются идемпотентно при startup/миграции. Регрессионный тест одновременно держит просроченную старую акцию и очередь нового root с комментариями: первым обрабатывается объявление нового поста. Это уменьшает задержку, но не даёт гарантий порядка сообщений относительно чужих Telegram-клиентов.


## Восстановление final: `message to be replied not found`

Это отказ Telegram отвечать на сохранённый discussion root: он удалён, недоступен или ID некорректен. Сам по себе текст ошибки не доказывает, кто/почему удалил сообщение. На фазе `final` денежный план уже обработан (`payouts_done=true`); возможны сохранённые pending-награды. Повторная отправка результата не должна переигрывать winner, выплаты или списание банка.

Обработка после обновления:
1. Как обычно, бот пытается отправить **одно** сообщение-ответ под постом, строго `allow_sending_without_reply=false`.
2. Только при конкретной ошибке отсутствующего reply-target переключается в `final_delivery_mode=edit_announcement`, сохраняет режим **до** запроса Telegram, затем заменяет собственное исходное объявление итогами (`start_message_id` в сохранённом `discussion_chat_id`). Не подставляет channel post ID вместо discussion ID, не отправляет результат без reply в общий чат, не выбирает случайный комментарий.
3. После timeout/рестарта повторяется уже edit, а не заведомо сломанный reply. `message is not modified` при edit означает, что нужный текст уже установлен; доставка завершается без повторных денег.
4. Если своего объявления нет/ID отсутствует/Telegram запрещает edit, выставляется `final_delivery_status=blocked`, `status=failed`, `terminal=true`. В логе одно сообщение `Campaign result delivery blocked`, а не ежеминутная бесконечная попытка. Финансовые записи не меняются, новые акции продолжают работать.
5. Прочие Telegram ошибки (например, HTML entities, сеть) не маскируются под исчезнувший root и используют прежний retry.

У успешно доставленного результата: `final_delivery_status=delivered`, `final_delivery_mode=reply|edit_announcement`, `final_message_id` — ID нового ответа либо ID отредактированного объявления. Старые кампании без новых полей совместимы; индексы/балансы мигрировать не нужно. Уже нетерминальные failed-final задачи из production-логов автоматически подхватываются после deployment новой версии.

Оператору при blocked: проверить `_id`, `discussion_chat_id`, `discussion_message_id`, `start_message_id`, `final_delivery_status`, `last_error`, `payouts_done` в `comment_campaigns`. Нельзя удалять rewards/journal, сбрасывать winner/phase в payout или повторно списывать деньги. Только после проверки доступного собственного сообщения в том же обсуждении можно исправить delivery target и повторно разрешить **final**-доставку (`terminal=false`, `status=processing`, просроченные due_at/lease_until; режим edit_announcement). Это ручная операция с backup/проверкой, не автоматическое угадывание ID. Если весь тред удалён, гарантированно опубликовать итог в нём уже невозможно.

Проверки: исчезнувший root → edit; timeout edit → restart → already-modified; root + announcement удалены → blocked без спама/общего чата; отсутствие сохранённого ID; посторонний BadRequest не включает fallback. Те же сценарии CI выполняет на настоящем MongoDB replica set. Они используют имитацию Telegram; факт публикации в production надо проверить после deployment.

## Переключение SQLite -> MongoDB по решению владельца

Владелец явно отказался от переноса старой локальной очереди: «старая база с комментариями не нужна, задача реализовать все в MONgo». Поэтому importer не запускается и runtime не читает/не удаляет старый SQLite. Только неприменённый локальный backlog остаётся за пределами новой очереди; уже записанные Mongo кампании/комментарии/победители/награждения/журнал/банк/кошельки и UUID сохраняются. Старые кампании могут продолжить завершение по имеющимся Mongo данным; забытый локальный хвост не учитывается.

Порядок после отдельного согласования deployment:
1. Остановить старый polling/worker; не запускать SQLite- и Mongo-версии одновременно. Auto-deploy из main тоже считается deployment.
2. Развернуть Mongo-only версию, оставить COMMENT_CAMPAIGNS_ENABLED=true и прежние channel/discussion/Mongo настройки. CAMPAIGN_INBOX_PATH можно удалить из Render Environment: больше не используется.
3. Startup сохраняет прежнюю identity, отмечает backend/schema, создаёт Mongo inbox indexes; никакие финансовые коллекции не очищает. Проверить /health/campaigns: enabled=true, ready=true.
4. Проверить новый пост -> короткое объявление -> комментарии -> завершение после deadline/grace, без повторных списаний. Не сбрасывать phase/winner/rewards старых кампаний.

Очереди без TTL: campaign_inbox_updates (bot/update/payload) и campaign_inbox_deletions (bot/chat/message/generation); ack удаляет только успешно обработанные записи. Повторное удаление получает новую generation; устаревший ack не удаляет новое событие. Mongo binding хранит identity, backend=mongodb, schema_version=2 и revision fence. Никаких mkdir/SQLite open/локальных файлов в inbox runtime нет.

Polling admission установлен до запуска Dispatcher.start_polling. Тест использует настоящий aiogram _listen_updates и проверяет удержание offset при Mongo outage и отмене. Это внутренний API aiogram: обновления библиотеки должны проходить эти regression tests. Обычные handlers остаются прежними; native/widget типы не отфильтровываются. Mongo outage задерживает polling, а Free sleep всё ещё не обеспечивает точность окончания через 4 часа.
