# 🦔 Ежа — нативная игра в сообщении

## Текущая версия: концепт «Успей погладить» · 7 секунд

Новые раунды `pet_once`: начать → за 7 секунд один раз коснуться ёжика или кнопки «Погладить» → забрать награду. Начальное/финальное нажатия не считаются поглаживанием. До дедлайна успел — стандартный приз +10% монет (целая часть, в пределах банка); не успел — стандартный приз. Повторные тапы ничего не накапливают. XP не меняется, серия не сбрасывается. Последний запрос в группах требует нажатия «Забрать награду» из-за запрета фоновых запросов SDK.

Оформление по присланному концепту: кремовая карточка, оливковая кнопка, крупный ёжик с закрытыми глазами, щёчками, колючками и рукой, сердечко и состояние «Ёжик доволен». Иллюстрация сделана DOM/CSS, без внешних ресурсов, рамки телефона и фиктивных кнопок звука/настроек. На итоговом экране показывается картинка из прежнего набора. Размер встроенного изображения адаптивный 128/96/64/48/32px, чтобы интерфейс и картинка вместе занимали не более 3900 байт zlib-9, оставляя запас до серверного лимита 4096. Проверены все 322 исходные картинки.

Длительность хранится при старте: новые сессии — 7 секунд, уже начатые `tap_bonus`/classic остаются 12-секундными с прежними правилами. Незавершённые результаты не перебрасываются, завершённые receipt не пересчитываются. Не начатые приглашения при новом вызове команды переводятся на `pet_once`. Описания накопительных +50% ниже — история предыдущей версии, а не правило нового раунда.


## Актуальные правила: стандартный приз + монеты за тапы

Новые сессии (`mode=tap_bonus`) **без случайного проигрыша и сброса серии**. Начать раунд → 12 секунд отдыха или поглаживаний → «Забрать награду» внутри того же виджета. Начальное и завершающее нажатия не являются бонусными поглаживаниями. Без поглаживаний выдаётся обычный daily с прежними бонусами серии и ограничением банка; XP не увеличивается за тапы.

Сервер засчитывает не чаще одного поглаживания за 1,5 секунды, максимум пять: каждое добавляет 10% от стандартной суммы монет (с учётом серии), максимум 50%, с округлением вниз до целой монеты. Пример для обычных 55 монет: пять зачтённых поглаживаний дают +27, итого 82 при достаточном банке. При исчерпании банка фактический дополнительный бонус может быть меньше или нулевым. Все нажатия дают локальный визуальный отклик; не каждое быстрое нажатие отправляет запрос Telegram.

`t1..t100` — номера отдельных запросов, не доверенный клиентский счётчик. Сервер проверяет владельца, дедлайн, временной интервал, последовательность и CAS счётчика; повтор/перезагрузка/вторая вкладка не увеличивают уже зачтённый тап. Перед выплатой раунд переходит в `settling`, фиксируя счётчик. Итог и монеты по-прежнему сохраняются одним атомарным user receipt.

В конце показываются фактическая награда, отдельная сумма монет за ласку и прежняя картинка из `src/infra/storage/ega`. Встроенное изображение выбирается из того же набора, автоматически уменьшается с 128 до 96/64 px при необходимости, чтобы весь HTML оставался до 4 KiB zlib-9, и отображается размером до 160×160.

В группах SDK запрещает фоновые запросы результата: после таймера нужна кнопка «Забрать награду». Никакой автоматической выплаты закрытой/незапущенной игры не обещается. Это остаётся нативным HTMLBubbles, а не внешней Mini App.

**Совместимость:** уже записанные результаты не пересчитываются. Старые сессии без нового mode сохраняют прежние правила 95%/5%; описание ниже про случайный исход относится к истории реализации и старым сессиям, а не к новым раундам.


## Что изменено

`/senseidaily`, «Ежа», прежние алиасы, ежедневный бонус из профиля и текстовые триггеры теперь отправляют **`sendWidget` прямо в текущий чат**, в том числе группу. Нет `WebAppInfo`, внешней кнопки запуска или перехода в личку/Mini App. Нажать на ежа для начала, гладить его нажатиями 12 секунд; последнее поглаживание после таймера запрашивает результат. Последний запрос совмещён с нажатием, поскольку **в группе widget-sandbox запрещает фоновые запросы**.

- Серверные 95% успеха / 5% неудачи, прежние награды и защита от повторного начисления сохранены.
- Успех внутри того же виджета: уведомление, фактические награды, серия и уменьшенная копия прежней картинки ежа. Исходный файл выбирается так же, как раньше, по session-токену.
- Картинка встроена как `data:` JPEG 64×64, показывается размером 96×96: внешние картинки sandbox запрещает, полный исходник не укладывается в лимит 4 KiB.
- Неудача: смешное сообщение, серия 0, без списания XP/монет. Одна попытка в день, 00:00 UTC.
- Перезагрузка виджета не меняет исход: новое нажатие возобновляет серверную сессию. Потерянный ответ можно запросить снова.
- Пересланные копии не играют (`is_shared=false`); чужой игрок не может использовать сессию владельца. Личность берётся из Telegram `widget_query.from`, не из HTML.

## Важное ограничение доставки — beta/test

Источники, проверенные при реализации:

- [widget-sandbox v0.6.0, формат доставки, раздел Bot API 10.4](https://github.com/TelegramMessenger/widget-sandbox/blob/v0.6.0/docs/tgw-format.md#the-bot-api-104)
- [Официальный conformance test-bot](https://github.com/TelegramMessenger/widget-sandbox/blob/v0.6.0/scripts/conformance/test-bot.ts)
- [SDK: запросы, ограничения по нажатию и группам](https://github.com/TelegramMessenger/widget-sandbox/blob/v0.6.0/docs/sdk-v1.md#214-requests-to-the-bot)

В upstream **указан Bot API 10.4 beta/test**: `https://api.telegram.org/beta/bot<token>/test/<method>`. Наличие методов в публичном production API и поддержка в обычном клиенте **не подтверждены**. Репозиторий sandbox сам по себе не добавляет их на сервер Telegram и не обновляет клиент пользователя.

По умолчанию бот остаётся на обычном production endpoint и пытается отправить документированный `sendWidget`. Если сервер отклоняет его/не знает метод, бот сообщает, что нативный виджет недоступен. **Попытка не расходуется, награда не начисляется, Mini App/GIF вместо виджета не подставляются.**

Для отдельного тестового бота/тестовых чатов с доступом к upstream beta:

```dotenv
TELEGRAM_WIDGET_BETA=true
```

Это **явный opt-in всего Telegram-транспорта**, включая polling: переключается endpoint на `/beta/bot…/test/…`. Не включать на обычном продакшен-боте с ожиданием, что его существующие чаты станут тестовыми. Нужны подходящий бот в тестовой среде, доступный beta API и клиент с включённым рендерингом виджетов. Настройку выполняют в секретном окружении развёртывания, не в чате и не в Git. `MINI_APP_URL` и публичный HTTPS-сайт для нативной игры не нужны.

Живой запрос в beta и отображение в реальном Telegram **не проверены**: в этой среде нет сетевого доступа к `api.telegram.org` и тестового Telegram-клиента. Успешные offline-тесты не доказывают доступность beta для конкретного бота.

## Реализация

- `src/widgets/hedgehog.py`: самодостаточный HTML, встроенные CSS/JS/картинка; `TelegramWidget.request`, без fetch/SDK Mini App и внешних ресурсов. Лимиты 32 KiB исходника / 4 KiB zlib-9 проверяются перед отправкой.
- `src/bot/native_widgets.py`: собственные классы документированных `sendWidget`, `answerWidgetQuery` до появления типизации в aiogram; ответы не более 1024 UTF-8 байт.
- `HedgehogWidgetMiddleware` обрабатывает будущие поля `widget_query`/`shared_widget_query` до стандартного диспетчера aiogram, который иначе их не распознаёт. Polling явно подписан на оба вида updates. Чужой пользователь, banned, пересылка, неправильное действие и maintenance отклоняются.
- Экономика использует существующие `HedgehogService`/`DailyService`: результат не вычисляется в JS. Атомарный user receipt предотвращает повторное начисление, включая старые Mini App-ссылки. Ограничение атомарности общего банка/журналов описано в [документации прежней реализации](HEDGEHOG_MINI_APP.md#безопасность-и-хранение).
- Старые HTTP-маршруты Mini App оставлены только для ранее отправленных ссылок; новые команды их не предлагают.

## Диагностика на реальном сервере (после обновления)

1. В `ADMIN_IDS` должен быть числовой Telegram ID администратора (настроить в окружении сервиса, не публиковать секреты).
2. Администратор пишет боту **в личку** `/senseiwidgetcheck`. Команда делает реальные запросы через текущий endpoint: сначала минимальный HTML, затем макет Ежа с его встроенной картинкой. `allow_queries=false`, тестовая строка вместо игрового токена; сервисы экономики не вызываются. Команда не меняет endpoint и не включает beta.
3. Читайте результат:
   - `method_or_route`: HTTP 404 / явная ошибка неизвестного метода. Проверить адрес API и наличие `sendWidget`; это не ошибка CSS и не повод вслепую включать beta.
   - `bad_request`: сервер отклонил параметры. Администратор получает очищенное описание Telegram; причину нужно разбирать по нему, поддержка метода не объявляется отсутствующей.
   - `payload`: ограничение/формат HTML или размеров. Если минимальный виджет принят, а Ежа нет — исправлять макет по точной ошибке.
   - `permissions` / `authorization`: права в чате или авторизация окружения.
   - `rate_limit` / `temporary`: лимит запросов, сеть или ошибка сервера; повторить позже.
4. Оба запроса приняты, но виджеты не видны: проверить клиентскую поддержку. Это отдельно от доступности API. Диагностика сама не может определить, что пользователь действительно видит на экране.
5. Оба виджета видны: вызвать `/senseidaily`, проверить старт, таймер и результат в настоящем чате. Приём `sendWidget` ещё не доказывает обработку `widget_query`.

У обычной команды ошибки теперь разделены по категориям; в сообщении есть короткий случайный код для поиска в логах `Native widget failure ref=...`. В очищенных логах сохраняются тип ошибки и описание Telegram, но не repr исключения с HTML/токенами. Токены, URL и session-параметры редактируются, описание ограничивается 700 символами. В обычном игровом сообщении точное описание ошибки не публикуется; оно доступно в приватной административной проверке.

Тестовая команда отправляет **два сообщения-виджета при успехе**, поэтому запускайте её осознанно. Это проверка доставки, не игровая попытка.

## Новый транспорт: напрямую MTProto layer 233

Теперь доступен **альтернативный путь**, не использующий HTTP `sendWidget`:

- `messages.sendMedia(InputMediaWidget)` отправляет HTMLBubbles прямо в текущий чат;
- `UpdateBotWidgetQuery` доставляет подписанные Telegram данные игрока;
- `messages.setBotWidgetQueryAnswer` возвращает итог внутрь того же виджета;
- серверная логика Ежа, один исход на день и атомарный receipt не меняются.

Добавлен полный генерируемый слой 233 на базе **официальной схемы Telegram Desktop**, а не ручная замена номера слоя в старом Telethon. Исходники клиента/генератора и схема закреплены commit + SHA-256. Генерация и двоичная сериализация/десериализация проверяются в CI без учётных данных Telegram.

### Настройка на Render

В секретном окружении сервиса (не в репозитории и не в чате):

```dotenv
NATIVE_WIDGET_TRANSPORT=mtproto
TELEGRAM_API_ID=<числовой app api_id>
TELEGRAM_API_HASH=<app api_hash>
TELEGRAM_WIDGET_BETA=false
```

`api_id` / `api_hash` берутся у вашего Telegram-приложения на `my.telegram.org` → API development tools. Это **не** BOT_TOKEN и не токен BotFather. Существующий `BOT_TOKEN` не менять: оба транспорта должны представлять **одного и того же бота**, что проверяется при подключении. Не отправляйте значения в переписку.

1. Установить зависимости из обновлённого `requirements.txt`, развернуть текущий main.
2. При первом включении сервер скачает проверенный pinned Telethon source с GitHub и сгенерирует runtime в `.cache`. Можно предварительно собрать `python -m src.infra.mtproto.bootstrap` на этапе сборки. Зависимости pyaes/rsa/setuptools установлены через requirements.
3. На старте создаётся **только бот-сессия в памяти**, без телефона/OTP/StringSession/файла с auth key. Проверяется совпадение ID с Bot API. Обычные команды остаются в aiogram/Bot API, виджеты идут через MTProto. При выключенном режиме скачивания/подключения MTProto не происходит.
4. Неправильные настройки/ошибка подключения в явно включённом режиме останавливают запуск, а не переключают среду молча. На хостинге нужны HTTPS-доступ к `codeload.github.com`, запись в `.cache` и доступ к Telegram MTProto DC. Текущий HTTP proxy для Bot API не переносится автоматически на MTProto.
5. После старта **отправить боту новое сообщение** в нужном чате. Это позволяет MTProto получить реальный `access_hash` чата/пользователя. Он никогда не подставляется равным нулю. При гонке с Bot API предусмотрено короткое ожидание; `peer_resolution` означает, что надо отправить новое сообщение и повторить.
6. Запустить в личке администратора `/senseiwidgetcheck`. Заголовок должен показывать **MTProto layer 233 / production**, не Bot API. Проверка и реальная игра используют один выбранный транспорт.
7. Если два макета видны в клиенте Telegram с поддержкой HTMLBubbles — вызвать `/senseidaily`, пройти раунд и проверить запрос/награду.

**Важно:** MTProto устраняет зависимость от отсутствующего HTTP-метода `sendWidget`, но не обходит серверные ограничения Telegram. `INPUT_MEDIA_WIDGET_NOT_ALLOWED` будет показан как `widget_policy`: сервер отклонил этот вариант запроса. Один отказ не устанавливает общий запрет боту: нужно отдельно сравнить чат, HTML и флаг запросов (см. раздел диагностики ниже). Разрешённый Telegram доступ нельзя добавить HTML/CSS. Beta автоматически не включается, подмены на GIF/Mini App нет.

Сетевое подключение к Telegram и отображение на реальном клиенте в этой среде не проверены. Тесты покрывают настоящие TL-конструкторы и round-trip response decoding, выбор транспорта, bot-only login/проверку ID/закрытие, запрет фиктивных access_hash, серверные отказы, запросы/награды обоих исходов без дублей, запрет чужого владельца, пересылок и wallet-запросов. MTProto wire-тесты требуют подготовленного runtime; CI явно собирает его перед pytest.

## Восстановление MTProto после `ConnectionError`

`ConnectionError` на минимальном макете означает ошибку транспорта; сам по себе он не доказывает запрет виджетов, неправильный HTML или конкретную причину разрыва. Раньше обёртка теряла контекст и показывала только имя исключения под `api_error`.

Теперь перед разрешением peer, отправкой медиа и ответом на запрос проверяется состояние клиента. При временном разрыве предусмотрено ограниченное переподключение с аутентифицированным `updates.getState`. Одновременные ошибки используют общий lock и поколение соединения, чтобы не переподключать клиент параллельно. На неоднозначном сетевом сбое `sendMedia` повторяется **не более одного раза с тем же request/random_id**, а не новым сообщением. Таймаут одной RPC-операции — 5 секунд, восстановления — 5 секунд; первая проверка и повтор могут занять до 15 секунд (при первоначально отключённом клиенте дополнительная проверка соединения может увеличить время). При позднем ответе внутри игры можно повторно нажать на ежа: финансовый receipt остаётся защитой от двойной награды. Это не бесконечный сетевой retry.

RPC-отказы (права, политика, авторизация, flood) автоматически не переотправляются. Закрытый при shutdown транспорт не подключается заново. Восстановление запускается отдельной задачей: Telethon `disconnect()` может отменить текущий Raw-handler; эта отмена не должна оборвать его собственное переподключение.

`/senseiwidgetcheck` показывает состояние до отправки и при сбое:

- `connected` — текущее состояние подключения клиента;
- `closed` — закрыт ли транспорт при shutdown;
- `updates` — зафиксированная ошибка фоновой задачи или `no_failure_recorded` (не доказательство здоровья канала);
- `reconnect_generation` — число успешных восстановлений в этом процессе.

Категория `temporary` теперь включает прежние сообщения `ConnectionError`/`TimeoutError`. Категория `transport_runtime` означает остановку обработчика обновлений или ошибку TL-декодирования: её нельзя скрывать циклом reconnect. Для неизвестного конструктора выводятся только класс ошибки и constructor ID, **без remaining bytes**, где могут быть приватные Telegram-данные. Для следующего исправления нужны этот код и очищенные логи `telethon.client.updates` вокруг момента остановки. Сам факт отсутствия ошибки в `_updates_error` не исключает проблем в других частях сети.

Живой разрыв соединения на Render этой средой не воспроизводится. Тестами воспроизведены отключённый клиент, потерянный ответ, таймаут, конкурентные запросы, отмена Raw-handler при reconnect, shutdown, сетевой сбой разрешения peer и остановка декодера. После деплоя повторить `/senseiwidgetcheck`, не меняя рабочие API_ID/API_HASH и не переключая beta.

## Исправление фонового `TypeError` при чтении Message

Локально воспроизведён конкретный дефект совместимости: Telethon после генерации подменяет `types.Message` своим friendly-подклассом (`telethon.tl.patched.Message`). Его рукописный `CustomMessage.__init__` остаётся от старого клиента и не принимает новые поля схемы 233: `from_rank`, `guestchat_via_from`, `rich_message`. Сгенерированный `from_reader` передаёт их **даже при отсутствующих flags** со значением None. Поэтому чтение обычного Message воспроизводило `TypeError: Message.__init__() got an unexpected keyword argument 'from_rank'`. Это не ошибка HTML/прав виджетов, а недостаточность прежнего покрытия тестами только TL-объектов виджета.

`src/infra/mtproto/compat.py` теперь устанавливает узкий адаптер friendly-конструктора при загрузке runtime **до подключения клиента**. Список новых optional-полей определяется из настоящих сгенерированных конструкторов Message/MessageService/MessageEmpty. Их значения и значения по умолчанию сохраняются на объекте, не отбрасываются; двоичная сериализация обратно даёт те же байты. Неизвестные аргументы не глотаются, новые обязательные поля не подменяются фиктивными значениями. Адаптер идемпотентен, класс/registry TL-конструкторов и права бота не меняются.

Bootstrap проверяет чтение/обратную запись обычного Message, а не только import и наличие InputMediaWidget. Версия cache marker изменена: старый runtime cache будет пересобран автоматически при следующем запуске MTProto-режима. API_ID/API_HASH/BOT_TOKEN менять не нужно.

Регрессионные тесты воспроизводят сбой без адаптера; проверяют Message, MessageService, MessageEmpty с пустыми и новыми optional-полями, вложенные Updates/updates.Difference, а также настоящий Telethon `_preprocess_updates` и сохранение access_hash в MemorySession. Диагностика фоновых ошибок дополнена последним местом traceback (имя файла, строка, имя функции), **без текста исходной строки, locals, сообщения исключения или remaining bytes**.

Предоставленный production-лог показывает только тип TypeError, без traceback, поэтому совпадение с этой локально воспроизведённой причиной окончательно подтверждается повторной проверкой на сервере. После деплоя перезапустить сервис, отправить новое сообщение и запустить `/senseiwidgetcheck`. Ожидается исчезновение этого TypeError; успешная отправка виджета/допуск сервера Telegram остаются отдельной живой проверкой. Если ошибка сохранится, новая безопасная позиция traceback укажет следующий несовместимый участок.

## `INPUT_MEDIA_WIDGET_NOT_ALLOWED`: различать чат и флаг запросов

Один RPC-отказ `INPUT_MEDIA_WIDGET_NOT_ALLOWED` подтверждает отклонение конкретного запроса, но не устанавливает общий запрет виджетов всему боту. До этой доработки `/senseiwidgetcheck` отправлял оба макета только с `allow_queries=false`, а игра использует `allow_queries=true`. Кроме того, проверка выполняется в личке, а исходная ошибка может возникать в группе. Успех прежней проверки не подтверждал допуск настоящего игрового варианта.

Теперь приватная admin-only команда явно показывает параметры и проверяет по порядку:

1. `minimal`: минимальный HTML, `allow_queries=false`.
2. `hedgehog`: полный HTML Ежа, `allow_queries=false`.
3. `minimal_queries`: тот же минимальный HTML, `allow_queries=true`.
4. `hedgehog_queries`: тот же полный HTML, `allow_queries=true`.

Во всех случаях `shared=false`. На первом отказе проверка останавливается, отказ автоматически не переотправляется. Если первые два варианта приняты, а третий отклонён, различие именно в флаге запросов, а не в оформлении Ежа. Если третий принят, а четвёртый нет, нужно исследовать полный макет при включённых запросах. Если все приняты, проверена только личка, не исходная группа. Принятие API по-прежнему не доказывает доставку `widget_query` и отображение клиентом.

Диагностический ёж содержит отдельный неигровой токен `diagnostic_no_game`: команда не создаёт сессию, не стартует раунд и не выдаёт ежедневную награду. Для живой проверки используется новое `/senseidaily`, а не диагностический макет. Транспорт, beta-окружение и `shared_widget` автоматически не переключаются.

Для отказа в группе нужен полный ответ этой команды (включая имя упавшего варианта и параметры), а не только запись о её вызове. Не присылать токены, API_HASH или сессионные строки. Логи обычного начисления за сообщения (`process_message_reward`, например +9 монет/+10 XP) не являются выплатой ежедневной награды Ежа.
