# Render: память, автобан и лотерея

Дата: 2026-11-26. Это проверка кода и локальные синтетические измерения, не диагностика работающего Render. Фактический лимит, конфигурация, загруженность, тариф, RSS и скорость production не известны.

## Новое поведение

- `on_user_leave`: автоматический бан применяется при добровольном выходе пользователя (`left`, инициатор — сам пользователь) из группы/supergroup, если автобан не отключён настройкой чата. Каналы, исключение администратором и выход ботов не подпадают под правило. Telegram должен присылать `chat_member`; для этого требуются соответствующие права бота и настройки доставки.
- `handle_user_left`: состояние бана, списание баланса, возврат в существующий SenseiBank, журнал и пометка всех не сожжённых записей билетов выполняются в одной транзакции MongoDB. Учитываются оба встречающихся флага `burned` и `is_burned`. Катана не изменяется. Повтор при уже активном бане не списывает деньги дважды. Транзакция требует MongoDB replica set/mongos; при отсутствии банка операция откатывается, новых монет не создаёт. На ошибке/неизвестном результате commit нужна сверка, нельзя автоматически проводить повторную конфискацию вслепую.
- `/unban_channels`: автоматический массовый возврат отключён, поскольку исторические баны за отписку и за выход из чата имеют одинаковую причину. Отличить их по ней нельзя: старая функция могла бы вернуть монеты и тем, кто действительно вышел из чата. Старые данные не изменялись; для исправления конкретного случая нужен индивидуальный аудит журнала и отдельное решение по возврату. Проверка подписки для доступа в личке — отдельный механизм и данной работой не удаляется.
- `/bonussensei [1–10]` работает в группе, где вызвана команда. Берутся только несожжённые билеты с текстовым `code`, чьи владельцы в момент проверок состоят в этом чате по Telegram. `restricted` допускается только с `is_member=True`; боты и выбывшие исключены. Проверка ошибки Telegram завершает розыгрыш до сжигания, а не молча исключает кандидата. Перед сжиганием выбранные владельцы проверяются повторно; выбранные билеты сжигаются в Mongo-транзакции с условной проверкой. Telegram и Mongo не предоставляют общей транзакции, поэтому абсолютную синхронность membership с commit гарантировать невозможно.
- Сохранена прежняя билетная модель: каждому действующему билету соответствует одинаковый шанс, один владелец с несколькими билетами может выиграть несколько раз. В RAM хранится пакет курсора и не более 10 выбранных билетов; вместо полной выгрузки и перемешивания применяется reservoir sampling.
- **Известное ограничение схемы:** некоторые исторические записи, например в `quiz_service`, хранят `amount` без индивидуального `code`; другие пути также используют разные поля. Такие записи не представляют собой однозначно идентифицируемые билеты для этой лотереи и не участвуют в розыгрыше. Они не мигрированы и не создаются автоматически: нужна отдельная инвентаризация данных и согласование правил конвертации. В автобане они помечаются изъятыми вместе с прочими активными записями. Число в уведомлении — число изменённых документов, а не обязательно сумма `amount`.
- Нет долговечной фиксации результата отправки розыгрыша: ошибка после Mongo commit, во время сообщения в Telegram, может оставить сожжённые билеты без объявления. Не запускать повтор до проверки состояния; следующий этап — durable draw receipt с идентификатором и восстановлением объявления. События выхода также не имеют отдельной долговечной очереди повторов: при сбое БД или пропуске Telegram update требуется операционная проверка. Не считать реализацию гарантией exactly-once.

## Что измерено локально

Среда: Linux sandbox, Python 3.11.2, aiogram 3.22.0, тестовый токен; это не поддерживаемый production runtime проекта (Python >=3.12), без Mongo/Telegram/Render.

- Один чистый импорт `src.main`: **2,029 с и max RSS 143,9 MiB** по `resource.getrusage`. Только один запуск, значения включают импорты и зависят от библиотек и окружения; не являются оценкой пиков production.
- Синтетический поток из **200 000 билетов одного владельца**, 10 победителей, поддельные Mongo cursor, транзакция и Telegram: **0,187 с**, `ru_maxrss` до и после 118,2 MiB. Это проверка алгоритма без сетей и сортировки Mongo, а не нагрузочный тест или замер реальной памяти Mongo/Render. Не позволяет оценивать время проверки большого числа разных владельцев.
- Ранее в `docs/OOM_ANALYSIS.md` описаны замеры Pillow и уже реализованная оптимизация картинок. Эти числа не воспроизводились в данной проверке; исходные общие выводы старого документа не следует считать доказательством текущей production-причины OOM.

## Приоритетный план для ограниченной памяти

1. **Наблюдаемость, без тяжёлых профайлеров постоянно.** Зафиксировать в Render реальный memory limit, RSS/HWM, перезапуски/OOM, задержку event loop, активные update/background tasks, длину очередей и p95/p99. Добавить лёгкую периодическую метрику RSS, не писать приватные данные. `tracemalloc`/heap dumps запускать только на отдельном стенде: они сами занимают память.
2. **Ограничить долгоживущие таблицы локов** (`economy_service._locks`, `daily_service._user_locks`, `daily_pet_service._locks`, `dojo_miner_service._locks`), TTL-кэши и общее число чатов digest. Lock нельзя удалять по TTL, пока его держат или ожидают: это создаст два независимых замка на одного пользователя. Подходы: bounded stripes с проверкой ложной конкуренции либо weak-value registry со строгими тестами конкурентности. Digest имеет до 1000 сообщений на чат, но количество чатов глобально не ограничено.
3. **Ввести budget конкурентности на входе**, учитывая критичные платежи, и ограничить число фоновых задач. Семaфор только внутри уже созданных update tasks не ограничивает память ожидающих задач; нужна именно ограниченная приёмная очередь/параллелизм polling с проверенной семантикой обработки и backpressure. Измерить lag и не допустить задержку платежей и капчи.
4. **Рендер:** нормализация части фото уже вынесена в thread под общим семафором и уменьшена стоимость JPEG, см. `daily_hedgehog.py` и `OOM_ANALYSIS.md`. На staging замерить пик двух одновременных тяжёлых изображений и GIF; при нехватке памяти уменьшать параллелизм и деградировать до статической карточки. Учесть PNG/WebP, время ожидания слота, отмену и объём загружаемых файлов. Не объявлять этот путь исправленным на Render без замера.
5. **Массовые операции:** лотерея больше не загружает все билеты в Python, но проверяет Telegram по каждому владельцу, последовательно, поэтому большие базы могут проходить долго и упираться в API limits. Mongo сортирует по `(user_id, _id)`; проверить `explain` и наличие индекса, стоимость сортировки и обращения к диску, прежде чем создавать индекс в production. Дальше возможно оптимизировать через устойчивый индекс членства с синхронизацией Telegram, но одни только активные пользователи из `chat_user_activities` не эквивалентны всем участникам и могут исключить молчащих игроков. Для рассылки и напоминаний ещё нужны курсоры, checkpoint и ограниченные воркеры.
6. **Горячий путь:** выяснить задержку Mongo и стоимость обновления профиля, достижений и Banzai. Не отключать транзакции или не менять частоту выдачи наград без отдельного решения о правилах экономики. `THROTTLE_RATE_LIMIT_MESSAGES=0` — существующее поведение, его изменение влияет на начисления.
7. **Деплой:** конфигурация Mongo replica set и права Bot API должны быть проверены перед выпуском; выполнить на изолированной replica set integration-тесты, сценарии повторной доставки и аварии. Включать постепенно с откатом и мониторингом. Бесплатный тариф может иметь ограничения на фоновые процессы и сон сервиса — фактические параметры необходимо проверить в текущей конфигурации пользователя.
