# Проверка экономики и логики Ежа — 2026-11-07

## Итог

**Полную финансовую атомарность подтвердить нельзя.** Повтор одного пользовательского receipt защищён, но общий банк и пользователь обновляются раздельно. Две воспроизводимые гонки отмечены `xfail(strict=True, raises=AssertionError)`, а не объявлены успешными тестами.

Область ручного разбора: `DailyPetService`, daily settlement, старый `claim_daily`, native widget bridge, сохранённый Mini App API, `/ega`. Полный pytest запускается по всему репозиторию, включая существующие тесты экономики, обмена, дуэлей, казино и других сервисов. Это регрессия проекта, не формальное доказательство корректности всех игровых сервисов. Тесты БД используют атомарные in-memory fakes, не живой MongoDB/реплика-сет. Telegram и production-баланс не затрагивались.

## Исправлено

1. **Отрицательная выплата старого daily-пути.** При отрицательном остатке банка `claim_daily` мог сформировать отрицательный `$inc` монет игрока. Доступная сумма теперь ограничена снизу нулём. Добавлены проверки -100, -0.5 и 0; XP не теряются, монеты игрока не списываются.
2. **Повтор daily через старый путь при недоступном журнале.** `claim_daily` теперь также проверяет авторитетный `hedgehog_day` в документе игрока. Если receipt уже сохранён, отсутствие `daily_claims` не разрешает повторное начисление через этот путь.
3. **Молчаливый отказ условного списания банка.** В базовом settlement и бонусах проверяется `matched_count`. Нулевое совпадение после user credit теперь явно попадает в ошибку сверки. Это сигнал об учётном расхождении, **не** исправление атомарности. Уже подтверждённая награда не отменяется; повтор того же query её не удваивает.

## Подтверждено тестами

- Базовая награда сразу, прежние XP/серия; повтор команды/перезапуск не создают второй receipt.
- +10% от фактически выданной базы, накопительное округление вниз, без сложного процента. Базы 0/1/9/10/11/55/105/305, по 20 принятых тапов.
- В нормальном пути сумма прироста пользовательских монет равна списанию банка и сумме бонусных записей журнала; XP/серия от тапов не меняются.
- Один пользователь, четыре независимых экземпляра сервиса, перемежающиеся чтения: CAS сохраняет все уникальные принятые запросы, повторные query ID не дают бонуса.
- Недостаток/ноль банка ограничивает выплату. При последующем пополнении текущая формула догоняет накопленное `floor(base*taps/10)`; это не сложный процент, но один последующий тап может покрыть недоплаченную часть предыдущих.
- Общее окно 15 секунд; повторы/переход/доставка не перезапускают его; исторические receipts сохраняют срок. После дедлайна новых обычных начислений нет. Для прежнего web API сохранено доверенное серверное время получения до DB-очереди.
- Владелец/private chat, ban, maintenance, HMAC прежнего web API и защита от пересылок покрыты существующими тестами.
- `/ega`: админ, личка, локальные счётчики, нет запросов выплат/создания daily receipt; кнопка возврата не платит и не перезапускает игру.
- Canvas в native strict sandbox и тестовый режим сохраняют работоспособность.

## Открытая проблема — высокий приоритет

`DailyService.settle_hedgehog` и `DailyPetService.tap` читают банк, атомарно обновляют **только игрока**, а затем отдельно списывают банк и пишут журнал. Персональный lock не сериализует разных игроков и не является межпроцессным lock общего банка.

Детерминированные воспроизведения в `tests/unit/test_daily_pet_audit.py`:

- Остаток банка **5**, два разных игрока одновременно читают его: начислено **10**, фактически списано **5**.
- Остаток банка **55**, два одновременных базовых daily: начислено **110**, фактически списано **55**.

В обоих случаях второе условное списание не проходит. Банк не становится отрицательным в этих двух путях, но монеты выпускаются без полного покрытия. Обрыв процесса между user credit и bank/journal write также оставляет несверенный receipt; повтор запроса не завершает пропущенные пост-записи автоматически.

### Что требуется дальше

Атомарный settlement user + bank + receipt/journal в MongoDB transaction (с проверкой поддержки replica set), либо отдельный устойчивый протокол резервирования/outbox со сверкой и восстановлением после неоднозначного commit. Недостаточно добавить asyncio-lock или слепо откатывать монеты игрока после сетевой ошибки: это не даёт межпроцессной/аварийной целостности. Архитектурный переход и миграция в рамках этой проверки не выполнялись.
