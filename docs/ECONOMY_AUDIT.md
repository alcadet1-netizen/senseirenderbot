# Проверка экономики и логики Ежа — 2026-11-06

## Итог

**Полную финансовую атомарность подтвердить нельзя.** Повтор одного пользовательского receipt защищён, но общий банк и пользователь обновляются раздельно. В двух ранее известных гонках (`tests/unit/test_daily_pet_audit.py`) теперь сначала выполняется атомарное списание банка, затем начисление игроку; при неудаче CAS банк возвращается. Эти тесты больше не `xfail`.

> **Обновление 2026-11-06 (глобальная эмиссия).** Введён жёсткий лимит **10 000 000 000 Coin** и один атомарный счётчик `bank/_id=single.total_emitted` (`EmissionService`). Начальное заполнение банка и стартовые наборы резервируются условным `$inc`; пустой банк больше не пополняется при чтении/выплате, а `process_game_win` при нехватке банка возвращает `insufficient_bank` вместо эмиссии. Это закрывает бесконечную эмиссию, но **не** делает перевод «банк → игрок» одной Mongo-транзакцией: остаточный риск описан ниже.

Область ручного разбора: `DailyPetService`, daily settlement, старый `claim_daily`, native widget bridge, сохранённый Mini App API, `/ega`. Полный pytest запускается по всему репозиторию, включая существующие тесты экономики, обмена, дуэлей, казино и других сервисов. Это регрессия проекта, не формальное доказательство корректности всех игровых сервисов. Тесты БД используют атомарные in-memory fakes, не живой MongoDB/реплика-сет. Telegram и production-баланс не затрагивались.

## Исправлено

1. **Отрицательная выплата старого daily-пути.** При отрицательном остатке банка `claim_daily` мог сформировать отрицательный `$inc` монет игрока. Доступная сумма теперь ограничена снизу нулём. Добавлены проверки -100, -0.5 и 0; XP не теряются, монеты игрока не списываются.
2. **Повтор daily через старый путь при недоступном журнале.** `claim_daily` теперь также проверяет авторитетный `hedgehog_day` в документе игрока. Если receipt уже сохранён, отсутствие `daily_claims` не разрешает повторное начисление через этот путь.
3. **Двойная выплата ставки в дуэли.** `_finish_duel` начислял `bet*2` как «награду победителя» и затем ещё раз из escrow. Второе начисление убрано: победитель получает ровно `bet*2`, а `duel_win` остаётся XP-записью с `coins_change=0`.
4. **Молчаливый отказ условного списания банка.** В базовом settlement и бонусах проверяется `matched_count`. Нулевое совпадение после user credit теперь явно попадает в ошибку сверки. Это сигнал об учётном расхождении, **не** исправление атомарности. Уже подтверждённая награда не отменяется; повтор того же query её не удваивает.

## Подтверждено тестами

- Базовая награда сразу, прежние XP/серия; повтор команды/перезапуск не создают второй receipt.
- +10% от фактически выданной базы, накопительное округление вниз, без сложного процента. Базы 0/1/9/10/11/55/105/305, по 20 принятых тапов.
- В нормальном пути сумма прироста пользовательских монет равна списанию банка и сумме бонусных записей журнала; XP/серия от тапов не меняются.
- Один пользователь, четыре независимых экземпляра сервиса, перемежающиеся чтения: CAS сохраняет все уникальные принятые запросы, повторные query ID не дают бонуса.
- Недостаток/ноль банка ограничивает выплату. При последующем пополнении текущая формула догоняет накопленное `floor(base*taps/10)`; это не сложный процент, но один последующий тап может покрыть недоплаченную часть предыдущих.
- Общее окно 15 секунд; повторы/переход/доставка не перезапускают его; исторические receipts сохраняют срок. После дедлайна новых обычных начислений нет. Для прежнего web API сохранено доверенное серверное время получения до DB-очереди.
- Владелец/private chat, ban, maintenance, HMAC прежнего web API и защита от пересылок покрыты существующими тестами.
- `/ega`: админ, личка, локальные счётчики, нет запросов выплат/создания daily receipt; кнопка возврата не платит и не перезапускает игру.
- Canvas в native strict sandbox и тестовый режим сохраняют работоспособность.

## Остаточный риск — высокий приоритет

`EmissionService.fold_legacy_bank()` при старте идемпотентно переносит старый `bank/_id=main.balance` в канонический `bank/_id=single.coins`; до и во время переноса `BankLedger` объединяет оба документа в один пул: чтение суммирует оба документа, списание идёт условными `$inc` по очереди с возвратом частичного списания. `EconomyService`, `AchievementService`, `DailyService`, `DailyPetService.tap`, `SlotsService`, `TradeService`, `QuizService`, `ExchangeService` и модерация работают через этот пул и списывают банк **до** начисления игроку. Поэтому конкурентный запрос не может выпустить монеты без покрытия: второе условное списание не проходит, а начисление не делается.

Это не Mongo-транзакция. Остаются два следствия:

- обрыв процесса между списанием банка и записью пользователя оставляет монеты в банке (эмиссия не растёт, но игрок не получил награду; нужна сверка/повтор);
- обрыв между начислением пользователю и записью журнала оставляет корректный баланс без journal-строки.

Для exactly-once выплат нужен reservation/outbox с восстановлением либо Mongo transaction на replica set. Автоматическая финансовая сверка пока не реализована.
